From text to attention

Every language model starts the same way: it cuts text into tokens, turns each token into a vector, stamps it with its position, and lets the vectors look at each other through self-attention. 1

Tokenization

A network can't read letters. It needs numbers, so the text is first cut into pieces taken from a fixed list, the vocabulary, and each piece is replaced by its position in that list. GPT-2's vocabulary has 50,257 entries, built with byte-pair encoding (BPE).

1.1 Split the text into chunks code

Before BPE runs, a regular expression cuts the text into rough chunks: runs of letters, runs of digits, punctuation and other symbols, whitespace, and English contractions like 's. A space is glued to the front of the word that follows it, so cat and ␣cat are different chunks and, later, different tokens. BPE never merges across chunk boundaries.

's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+

How the pattern is read.

  1. The | signs split it into 12 alternatives. Each one describes one kind of chunk (see the table below).
  2. The regex engine walks through the text from left to right. At the current position it tries the alternatives in the order they are written, from 1 to 12.
  3. The first alternative that matches wins, even if a later one would match a longer piece. Its match becomes a chunk, and the engine carries on right after it.

The order matters. In a␣␣␣b, at the spaces alternative 11 matches ␣␣ and wins, although alternative 12 could take all three spaces. The last space is left for the next word: a · ␣␣ · ␣b. And since the contractions are written in lowercase, it's splits as it · 's but IT'S as IT · ' · S.

Symbols: \p{L} any letter in any script · \p{N} any numeric character (digits, but also ², ½, Ⅻ) · \s any whitespace · [^…] any character except the listed ones · ␣? an optional space · + one or more · (?!\S) "only if the next character is not a non-space". Why split first at all? Without it, BPE would waste vocabulary on variants like dog. dog! dog?, so GPT-2's authors stop merges across character categories, with an exception for the leading space (Radford et al., 2019, §2.2).

1.2 Merge bytes into tokens (BPE) code

Each chunk is turned into its UTF-8 bytes. GPT-2 gives each of the 256 possible bytes a printable stand-in character, so a space byte is written Ġ. Then one rule is repeated: among all neighbouring pairs, find the one that comes earliest in the learned merge list merges.txt and glue it together everywhere in the chunk. When no neighbouring pair is in the list, BPE stops. Frequent words end up as one token, and rare words stay in pieces. Where this list comes from is shown step by step in the interlude on tokenizer training after this section.

1.3 Look up token IDs in vocab.json code

vocab.json is the tokenizer's dictionary: one JSON object with 50,257 entries of the form "token": ID. The keys are written in GPT-2's byte alphabet from 1.2, so a leading space is Ġ (stored in the file as \u0120), and the values are the integers 0 to 50,256. Each final piece from 1.2 is looked up there to get its token ID. The ID carries no meaning by itself: it is a row number, and in step 2 it selects row ID of the embedding matrix. This list of integers is all the model ever sees of your text.

The numbering follows the training order (see T.3): IDs 0–255 are the single bytes, then every merge rule adds the next ID (rule #1 created ID 256, rule #506 created ID 761 Ġneed), and the last ID, 50,256, is <|endoftext|>. So a small ID means a token that was merged early, which means a very common one.

T

Interlude: how the tokenizer is trained

Step 1.2 used a list of 50,000 merge rules, merges.txt. Nobody wrote this list by hand: it is the output of training the tokenizer, which was done once, before GPT-2 itself was trained. This training is plain counting, with no neural network involved. Below is the whole procedure on a text you can edit, and then the same idea at GPT-2's scale.

T.1 Start: a training text and 256 bytes

Training needs a sample of text. GPT-2's tokenizer learned from a large amount of web text; here a few lines are enough. The text goes through the same pre-tokenization as in 1.1, and identical chunks are counted: from now on only the chunks and their counts matter. Every chunk starts as single bytes, so the starting vocabulary is just the 256 possible bytes. That is already enough to write down any text, but only at one token per byte.

T.2 One round of training, up close

A round has four moves. Count how often every pair of neighbouring symbols occurs in the whole text. Pick the pair with the highest count. Merge it everywhere into one new symbol. Write it down: the pair becomes the next line of merges.txt, and the new symbol becomes the next entry of the vocabulary. Step through the rounds below.

T.3 Repeat, and watch the text get shorter

Every round glues the most common pair, so the training text loses one symbol for every place the pair was glued. Training is greedy compression: each round makes the biggest saving a single new token can make. The rounds go on until the vocabulary has the size you want. GPT-2's authors stopped after 50,000 rounds, and that is the whole reason merges.txt has 50,000 lines. Two files come out of training: merges.txt, the rules in the order they were learned, and vocab.json, which gives every token its ID. Line n of merges.txt is the token with ID 255 + n. Adding the 256 bytes and the special token <|endoftext|> gives 256 + 50,000 + 1 = 50,257 tokens.

T.4 Why the output is a list of rules, not just a list of tokens

You might expect training to output only the vocabulary. But a vocabulary alone does not say how to cut a word: most words can be spelled with its tokens in several ways. The ordered list of merges settles this. Replaying the rules in the order they were learned gives exactly one answer, the same every time, for training text and new text alike. The list also records which two pieces each token is made of. The vocabulary adds no information of its own: vocab.json can be rebuilt from merges.txt, as the check below does with GPT-2's real files. That is why the IDs in 1.3 follow the rule numbers. (Other tokenizers answer "how to cut" differently: WordPiece, used by BERT, takes the longest token that fits from the left, and Unigram, used by T5, picks the most probable split.)

T.5 The rules also work on text they have never seen

merges.txt is a procedure, not a list of memorized words. Running your rules in order on new text is exactly what step 1.2 does with GPT-2's 50,000 rules. Words that never appeared in the training text still break into familiar pieces. And any text at all can be tokenized, because in the worst case it falls back to single bytes.

T.6 The same at GPT-2's scale: what if training had stopped earlier?

Each round only adds a rule at the end of the list, so the first N lines of GPT-2's merges.txt are exactly the tokenizer that training would have produced had it stopped after N rounds. Move the slider to tokenize your sentence from the top of the page with only the first N rules. More rules make texts shorter in tokens, but every rule adds a token, and every token adds a row of 768 learned numbers to the embedding matrix W_E in step 2.

2

Token embedding

An ID is only a label: token 8086 is not "bigger" than token 318. So each ID is swapped for a list of 768 learned numbers, its embedding. During training these numbers were nudged until tokens that are used in similar ways got similar vectors.

2.1 Read one row of the embedding matrix per token code

All embeddings live in one matrix W_E with one row per vocabulary entry: 50,257 rows × 768 columns ≈ 38.6 million numbers, almost a third of GPT-2 small's 124 M parameters. Embedding a token is nothing more than reading row number ID. Mathematically it is a one-hot vector times the matrix, but nobody computes it that way.

e_i = W_E[id_i]

2.2 Similar tokens, similar vectors

Two embeddings can be compared with cosine similarity, the cosine of the angle between them. 1 means they point the same way and 0 means unrelated. Individual dimensions don't have human-readable meanings. The information is in the pattern as a whole. Note that The and ␣the are different tokens with different, but related, vectors.

cos(e_i, e_j)

Identical tokens get identical vectors wherever they appear. At this point the model has no idea of word order.

3

Positional encoding

Self-attention (step 4) compares every token with every other token, but the comparison itself ignores order: shuffle the input vectors and, without the causal mask, the outputs come out shuffled the same way. To attention, dog bites man and man bites dog would be the same bag of vectors. So before attention, GPT-2 adds to each token a second vector that depends only on its position.

3.1 GPT-2 learns a table of positions code

GPT-2 learns a second matrix W_P during training. It has 1,024 rows (the longest input GPT-2 can read) × 768 columns. Position 0 uses row 0, position 1 uses row 1, and so on, whatever token sits there. The original Transformer (Vaswani et al., 2017) used a fixed formula instead. Every pair of dimensions is a sine/cosine wave with its own wavelength, so each position gets a unique, smoothly changing fingerprint. Toggle between the two below.

p_i = W_P[i]

3.2 Add them: token + position code

The input to the first Transformer block is the element-wise sum of the two vectors. It is still 768 numbers per token, with no concatenation. The same word at two different positions now has two different vectors.

x_i = e_i + p_i
4

Self-attention block 1 of 12

Attention lets every token pull in information from the tokens before it. Each token makes three vectors from its embedding: a query (what am I looking for?), a key (what do I contain?) and a value (what do I hand over if I'm picked?). How well token i's query matches token j's key decides how much of j's value flows into i.

Attention(Q,K,V) = softmax(QKᵀ/√d_k + M) V

4.1 Normalize each token (LayerNorm) code

GPT-2 first normalizes every token vector on its own: subtract its mean, divide by its standard deviation, then apply a learned per-dimension scale γ and shift β. This keeps the numbers in a stable range however large the embedding is. (GPT-2 does this before attention, a design called "pre-LN".)

x̂_i = γ ⊙ (x_i − μ_i)/σ_i + β

4.2 Project to queries, keys and values code

Three learned matrices turn each normalized vector into a query, a key and a value. GPT-2 stores them side by side as one 768 × 2,304 matrix (c_attn), so a single multiplication produces all three. Each output number is a weighted sum of all 768 inputs plus a bias.

[Q|K|V] = X̂ W + b

Multi-head split. Each 768-long vector is then cut into 12 slices of 64. Slice h of every query, key and value belongs to head h, and the 12 heads run attention independently and in parallel. The highlighted slice below is the selected head. Click another slice to switch.

q_i^(h) = q_i[64h : 64h+64]

4.3 Score every pair: query · key code

For the selected head, the score between query token i (row) and key token j (column) is the dot product of their 64-number slices: multiply them position by position and add everything up. A large positive score means a strong match. Hover or click a cell to see the 64 products that make it up.

s_ij = q_i · k_j

4.4 Scale, then hide the future code

Scale. A sum of 64 products can get large, and softmax over large numbers is almost all-or-nothing. Dividing by √64 = 8 keeps the scores in a range where several tokens can share attention. Mask. GPT-2 is trained to predict the next token, so a token must not peek at the tokens after it. Every score with j > i (above the diagonal) is replaced by −∞, and softmax turns −∞ into exactly 0.

s'_ij = s_ij/8 if j ≤ i else −∞

4.5 Softmax: scores become weights code

Softmax turns each row of scores into attention weights that are positive and add up to 1: exponentiate each score, then divide by the row total. Row i answers the question "how much should token i listen to each earlier token?"

a_ij = exp(s'_ij) / Σ_k exp(s'_ik)

4.6 Blend the values code

The head's output for token i is a weighted average of value vectors, with the attention weights as the mix. If token i puts 90% of its attention on one token, its output is almost a copy of that token's value. This is how information moves between positions.

z_i = Σ_j a_ij v_j

4.7 Twelve heads, side by side code

All 12 heads follow the same recipe, each with its own slice of the weights, so they learn different habits. Even in this first layer you can spot some: heads that mostly look at the token itself, heads that look at the previous token, and heads that put their attention on the first token, a common "nothing to do here" default sometimes called an attention sink. Click a head to inspect it. Their 12 outputs of 64 numbers are then glued back together into one 768-number vector.

z_i = [z_i^(0) | … | z_i^(11)]

4.8 Mix the heads and add back the input code residual

One more learned matrix W_O (768 × 768, c_proj) mixes what the 12 heads found. The result is then added to the token's vector from step 3. This residual connection means attention contributes an update to each token instead of replacing it.

h_i = x_i + z_i W_O + b_O

What happens next

The vectors h_i go through a second LayerNorm and an MLP (768 → 3,072 → 768), then through 11 more blocks exactly like this one. The last block's vector is finally compared with all 50,257 token embeddings to score every possible next token. Transformer Explainer shows that part, including temperature and sampling.
